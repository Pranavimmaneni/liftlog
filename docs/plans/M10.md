# M10 Food data and engines: plan

Requirements: `docs/PRD-1.2.md` (1.2.0 draft, approved mockups in `design/screens-v2/food/`). M10 builds everything under the Food section's UI: the food library, the data model, the repositories and the pure engines, each tested before any screen exists (CLAUDE.md "engines first"). The Food screens are M11; combined feedback screens and quests UI are M12.

**Exit criteria**
- `npm run seed:foods` builds the library deterministically from pinned sources; `FOOD-SEED-REPORT.md` lists counts, every filter and every drop reason.
- Schema v2 migrates a v1 database and restores a v1 backup without changing any training data (migration tests).
- Every engine below has Vitest tests named after its requirement ID; `src/engine` stays ≥ 90% line coverage.
- `/dev/food` (dev page, like `/dev/poses`) searches the whole library offline on a phone in under 150 ms and shows the target maths for a sample profile.
- Typecheck, lint, unit and e2e pass; first-load JS < 250 KB gz; precache < 5 MB (the food library is not precached).
- No change to any LiftLog screen. Nothing user-facing ships yet, so no release; `main` stays deployable.

## 2. Schema v2 and repositories (NFR-REL-6, FR-SHR-1/2, FR-DIARY-*, FR-FAST-1)

Schema v2 is **additive**: new tables and new optional profile fields only; no v1 row is rewritten.

| Table | Key and indexes | Fields |
|---|---|---|
| `foodLib` | `id, *terms, gtin` | imported library rows (not backed up, rebuilt from the chunks; D12 pattern) |
| `foods` | `id, *terms, gtin, isRecipe` | the user's own foods and recipes (`ingredients[]`), backed up |
| `diary` | `id, date, [date+meal], loggedAt` | date, meal, loggedAt, foodId, grams, portion label, servings, **nutrient snapshot per 100 g** (edits to a food never rewrite history) |
| `savedMeals` | `id` | name, items[] |
| `fasts` | `id, startedAt` | startedAt, endedAt?, planHours |
| `profile` (existing) | – | + heightCm?, activity?, phase?, rateKgPerWeek? |
| `settings` (existing) | – | + food keys: target overrides, carb cycling, last section (FR-NAV-2) |

## 3. Engines (pure, no Dexie/React, `now` passed in)

Every number comes from `data/nutrition.json` or `data/dri.json` (NFR-MAINT-2).

| Engine | What it does | Req |
|---|---|---|
| `engine/nutrition.ts` | scale per-100 g to a portion; sum a meal/day; `null` = unknown (never 0) with a "known for N of M items" count; recipe totals from ingredients and yield | FR-DIARY-2, FR-FOOD-5 |
| `engine/energy.ts` | Mifflin-St Jeor BMR; activity factor including training days from the routine; phase adjustment from the weekly rate (≈ 7,700 kcal per kg); calorie floor; the reason text ("You burn about 2,700. Plus 250 to gain slowly.") | FR-TGT-1, FR-TGT-2 |
| `engine/macros.ts` | protein g/kg by goal and phase (ISSN range), fat floor g/kg, carbs = the rest, fibre per 1,000 kcal; training-day carb shift; overrides with "Reset to coach's pick" | FR-TGT-3, FR-TGT-6 |
| `engine/micros.ts` | DRI targets by sex and age for the 8 micros (sodium as a limit); upper-limit flags; missing sex → the lower value, as S19 does | FR-TGT-4 |
| `engine/adaptive.ts` | trend weight (exponentially smoothed weigh-ins); after ≥ 21 days with ≥ 14 logged days, estimated expenditure from intake vs trend change; a new target only when it differs by > 100 kcal | FR-TGT-5 |
| `engine/food-search.ts` | the exercise search (FR-LIB-3) extended with brand and alias terms; own foods, favourites and frequent foods first; prefix index for 30k rows | FR-FOOD-3, NFR-PERF-5 |
| `engine/training-link.ts` | what Food reads from LiftLog: usual training time (median start of the last 6 sessions, else none), training days, weekly volume change, e1RM trend, bodyweight | FR-COACH-3, FR-SHR-1 |
| `engine/food-review.ts` | weekly / monthly: days on target, average % per macro, micro adequacy on known data only, "low this week" (< 70%), top food sources per nutrient | FR-NUT-1, FR-NUT-2 |
| `engine/coach.ts` | combined insights in order, first match for "Going well" and "Needs work", each with a reason and a fix: protein short on training days; < 30 g carbs in the 3 h before a session; gain phase with flat trend weight for 3 weeks; losing > 1%/week while e1RM drops; a micro < 70% with foods rich in it from the user's own diary first | FR-COACH-1, FR-COACH-2 |
| `engine/fasting.ts` | elapsed / remaining from timestamps; presets; "N in a row"; whether the usual training time falls in the fast | FR-FAST-1 |
| `engine/food-quests.ts` | daily quests (protein, pre-lift carbs, fibre) and a weekly quest; XP from `xp.json` additions, derived from the diary, added to the shared level (FR-XP-1 rules: derived, never stored) | FR-GAME-1 |

Constants: `data/nutrition.json` (activity factors, phase rates, protein/fat per kg, fibre, carb shift, floors, on-target tolerance, coach thresholds, quest XP), `data/dri.json` (values transcribed from the National Academies DRI tables, with the citation), `data/xp.json` (food quest entries).

## Decisions to log when the work starts

- Library rows live in Dexie (`foodLib`), not in memory or the SW cache, so search works offline and survives iOS cache eviction.
- The library downloads in the background after first load (≈ 2 MB compressed), outside the precache.
- Nutrient snapshot per diary entry, so editing or re-importing a food never changes past days.
- `null` means "unknown"; reviews only judge days and nutrients with known data.
- LiftLog has no planned workout times, so Food uses the usual training time from history.
- Food streak = consecutive days with food logged in at least 2 meals; quests (not the streak) reward hitting targets.
- M10 work stays on branch `m10-food-data` until M11 can use it, then merges to `main`; the v2 migration is additive and Pranav is asked to make a backup before the first deploy with it.
